# Google H5 Ads setup (bloodinthebayougame.com)

This is a **configured publisher with ads still disabled**, not live monetization. The shared script is in
both the Next layout head and the game iframe head. Only the game document may
load Google's tag: Google requires the tag, canvas, and adBreak calls in the same
document. The web publisher ID is `ca-pub-9730543201329278`, supplied by the owner.
No Google SDK is loaded by default, and no revenue is generated by this configuration alone.

## Website account activation

The supplied account screenshot lists **AdMob** as the only active product. That
is not evidence of AdSense for Content or H5 Games Ads approval. Use the same
Google account to [apply for the AdSense account upgrade](https://support.google.com/adsense/answer/6023158?hl=en),
connect `bloodinthebayougame.com` as instructed by Google, and
[apply for H5 Games Ads access](https://support.google.com/adsense/answer/1705831?hl=en-GB).
Approval is not guaranteed. Do not flip the code's enable/consent switches merely
because an AdMob unit has been created.

## Before enabling

1. Complete AdSense H5 Games Ads eligibility/site approval for bloodinthebayougame.com
   and obtain your AdSense publisher ID. Configure privacy disclosures, a suitable
   consent-management platform, and Google's required publisher/site files using
   the exact values supplied in your Google account.
2. The owner's `publisherId` is set in `public/game/ads.js`; keep `testMode: true` during testing.
   Set `enabled: true` only after review. Your CMP must set `consentGranted` according
   to the applicable consent requirements, then call `bayouAds.initialize()` inside
   the iframe. The boolean is only an integration gate, not a consent platform.
3. Connect retry and next-level **user actions** to the functions below. They are
   deliberately not wired to death/mission timers. Implement synchronous pause/mute
   and exact prior-state restoration, including multiplayer behavior and all audio.
4. Test ad shown, no-fill, blocked SDK, consent denied, and duplicate clicks. Remove
   test mode only after Google approval and consent/policy verification.

```js
// In the game iframe, from a retry/continue button handler:
const accepted = window.bayouAds.gameOver({ // or .levelComplete(...)
  pauseAndMute() { /* Save state; synchronously pause gameplay and mute all audio. */ },
  restore() { /* Restore the saved gameplay and audio state after an actual ad. */ },
  done(info) { /* Continue retry/next-level flow, even when no ad was available. */ },
});
if (!accepted) {
  // Continue normally: disabled, not ready, consent absent, or another break pending.
}
// Update alongside the game's mute control:
window.bayouAds.setSound(false);
```

Do not use these empty example callbacks in production. A true return means the
placement was submitted, not that an ad was shown. Never block gameplay waiting
for SDK readiness. These triggers use Google's `next` placement for a user-driven
restart/next-level transition, with distinct reporting names.

## Owner-supplied iOS AdMob configuration (not integrated yet)

These public identifiers are transcribed from the owner's iOS ad-unit creation
screen, not invented test values:

- iOS app ID: `ca-app-pub-9730543201329278~2335600781`
- iOS interstitial ad unit: `ca-app-pub-9730543201329278/8884513486`

**Do not put the iOS unit in `admob.interstitialSlot` below.** Google's H5
AdMob bridge is Android-only. iOS needs a native Google Mobile Ads SDK integration
with its own interstitial loading/presentation and consent flow. The app ID goes
in the native `GADApplicationIdentifier` Info.plist entry after the SDK is added;
it is not a website publisher ID or an ad-unit ID.

An older Capacitor Xcode project exists inside
`public/downloads/blood-in-the-bayou-ios.zip`; it has no Google Mobile Ads SDK,
consent integration, or ad presentation bridge. Its bundled game is separate
from the website. The archive has not been changed: first confirm that it is the
maintained app source (or supply the current app repository) before integrating
and regenerating an App Store download. A website deployment does not update an
installed iPhone app.

Native release requirements:

1. Add Google Mobile Ads and consent handling in the maintained iOS project.
2. Use Google's iOS test interstitial ID during development, not the owner's live
   unit: `ca-app-pub-3940256099942544/4411468910`.
3. Wire ads only to natural retry/next-mission user actions. Pause gameplay and
   all audio for an actual ad, restore the prior state on dismissal/failure,
   preserve ad-free purchases, and continue without waiting when no ad is ready.
4. Verify shown/no-fill/failure/consent-denied/ad-free paths in Xcode and on a
   physical iPhone, complete Google app readiness/privacy requirements, then
   archive/sign and release a new App Store build using the owner's live unit.

Native setup is **not implemented** by the website publisher configuration.
See [Google's iOS interstitial guide](https://developers.google.com/admob/ios/interstitial).

## AdMob (optional Android app, not the website)

Create/configure your Android app and interstitial ad unit in your own AdMob
account. Add the Google Mobile Ads SDK to the native host and register its WebView
with `MobileAds.registerWebView`. Set `admob.interstitialSlot` to the issued ad unit
ID; retain the AdSense publisher ID too. `rewardedSlot` is reserved for future
rewarded integration; these triggers do not request rewarded ads or grant rewards.
There is no native Android host in this repository, and no Google account was
created or configured by this change. iOS support is not implied.
